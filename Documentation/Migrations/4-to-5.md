# Migration 4 -> 5

This guide eases the transition of the existing apps that use Swift Package List 4.x to
version 5 of the tool.

### Minimum Requirements

```diff
- Swift 5.9
+ Swift 6.2

- macOS 10.15
+ macOS 11.0
- Mac Catalyst 13.0
+ Mac Catalyst 15.0
- iOS 13.0
+ iOS 15.0
- tvOS 13.0
+ tvOS 15.0
- watchOS 6.0
+ watchOS 8.0
  visionOS 1.0
```

## Package Name

The package name changed from `SwiftPackageList` to `swift-package-list`. This should
not require any manual migration steps: the library product and module names remain
`SwiftPackageList` and `SwiftPackageListUI`, so existing imports continue to work.

## `stdout` Output Type and Default Output

The `stdout` output type got removed. Output format and destination are now configured
separately: use `--output-type json` to print JSON to the console and add `--output-path`
to write it to a file:

```shell
// Swift Package List 4
swift-package-list Test.xcodeproj --output-type stdout

// Swift Package List 5
swift-package-list Test.xcodeproj --output-type json
```

The default output type is now `table`, which prints a compact dependency summary.
Commands that relied on the default JSON output need an explicit output type:

```shell
// Swift Package List 4
swift-package-list Test.xcodeproj

// Swift Package List 5
swift-package-list Test.xcodeproj --output-type json
```

> [!IMPORTANT]
> JSON and Property-List output now go to the console when `--output-path` is omitted.
> Keep `--output-path` in scripts that generate `package-list.json` or `package-list.plist`.
> PDF and Settings Bundle output still require an output path.

For example, a Run Script Phase that generates a JSON file should use:

```shell
swift-package-list "$PROJECT_FILE_PATH" --output-type json --output-path "$OUTPUT_PATH" --requires-license
```

The build-tool plugin continues to generate JSON files by default. `stdout` is no longer
an option in its configuration.

## License Detection Changes

Swift Package List 5 recognizes more license filenames. Dependencies that were previously
excluded by `--requires-license` because their license files were not detected may now
appear in the generated output. This also affects the build-tool plugin, which requires
licenses by default.

If a dependency should remain excluded, specify its identity explicitly:

```shell
swift-package-list Test.xcodeproj --requires-license --ignore-package example-package
```

For the build-tool plugin, add the identity to `ignorePackages` in the target's
configuration instead.

## Regenerate Acknowledgments and the Settings Bundle

The generated PDF and Settings Bundle files now use the `Acknowledgments` spelling:

```diff
- Acknowledgements.pdf
+ Acknowledgments.pdf

- Settings.bundle/Acknowledgements.plist
+ Settings.bundle/Acknowledgments.plist
- Settings.bundle/en.lproj/Acknowledgements.strings
+ Settings.bundle/en.lproj/Acknowledgments.strings
```

It is recommended to start from scratch: remove the old generated acknowledgment files
and regenerate them with Swift Package List 5. Regenerating the Settings Bundle also
includes the newly supported languages and updated translations. If your Settings Bundle
contains custom settings or translations, keep a copy and reapply them after regeneration.
Update file references in your project and scripts, including localized `.strings` files
for the other languages.

If you keep an existing Settings Bundle, update the Child Pane entry in `Root.plist`:

```diff
  <key>Type</key>
  <string>PSChildPaneSpecifier</string>
  <key>Title</key>
- <string>Acknowledgements</string>
+ <string>SPL_ACKNOWLEDGMENTS_TITLE</string>
  <key>File</key>
- <string>Acknowledgements</string>
+ <string>Acknowledgments</string>
```

Update the corresponding localization key in each `Root.strings` file as well:

```diff
- "Acknowledgements" = "Acknowledgements";
+ "SPL_ACKNOWLEDGMENTS_TITLE" = "Acknowledgments";
```

> [!IMPORTANT]
> Existing `Root.plist` and `Root.strings` files are preserved during generation, so these
> changes must be made manually. Remove obsolete `Acknowledgements.plist` and
> `Acknowledgements.strings` files once the references have been updated.

## Library API Changes

### Bundle Acknowledgment Lookups

The `acknowledgementsURL` and `acknowledgementsPath` properties have been renamed to use
the `acknowledgments` spelling. Use the format-based API to look up the regenerated files:

```swift
// Swift Package List 4
let url = Bundle.main.acknowledgementsURL
let path = Bundle.main.acknowledgementsPath

// Swift Package List 5
let url = Bundle.main.acknowledgmentsURL(format: .pdf)
let path = Bundle.main.acknowledgmentsPath(format: .pdf)
```

The format-based API also supports `.html` and `.markdown`. The `acknowledgmentsURL` and
`acknowledgmentsPath` properties without a format parameter are deprecated.

### `Package.repositoryURL` and Initializers

The deprecated `repositoryURL` property and the initializers without a `kind` parameter
got removed. Use `location` and specify the package kind when creating a `Package`:

```swift
// Swift Package List 4
let package = Package(
    identity: "example-package",
    name: "ExamplePackage",
    version: "1.0.0",
    branch: nil,
    revision: nil,
    repositoryURL: URL(string: "https://github.com/example/example-package")!,
    license: "The license text"
)
let repositoryURL = package.repositoryURL

// Swift Package List 5
let package = Package(
    kind: .remoteSourceControl,
    identity: "example-package",
    name: "ExamplePackage",
    version: "1.0.0",
    branch: nil,
    revision: nil,
    location: "https://github.com/example/example-package",
    license: "The license text"
)
let location = package.location
```

The `location` is a `String`: it can contain a repository URL, a local path or an empty
string for a registry package. Convert it to a URL only when appropriate for the package
kind. Existing calls to the initializer with `location` also need the `kind` argument.

An empty license string now makes `Package.hasLicense` return `false`. Such packages are
also excluded by `--requires-license`; this applies to custom packages as well.

## Plugin Configuration

The preferred configuration filename is now `.swift-package-list.json`. The previous
`swift-package-list-config.json` filename is still supported; if both files exist, the
plugin uses `.swift-package-list.json`.

Configuration files without a `version` field continue to use the version 1 format. To
adopt version 2, add `"version": 2` and move the `project` options into `targets["*"]`:

```json
// Swift Package List 4
{
    "project": {
        "outputType": "plist",
        "requiresLicense": false
    },
    "targets": {
        "App": {
            "outputType": "json"
        }
    }
}

// Swift Package List 5 (configuration version 2)
{
    "version": 2,
    "targets": {
        "*": {
            "outputType": "plist",
            "requiresLicense": false
        },
        "App": {
            "outputType": "json"
        }
    }
}
```

The `"*"` entry supplies options for targets without an explicit entry. An explicit target
entry uses plugin defaults for omitted options; it does not inherit from `"*"`.

Paths such as `projectPath` and `customPackagesFilePaths` are resolved relative to the
project directory. See the [Build Tool Plugin documentation](../CommandLineTool/BuildToolPlugin.md#environment)
for environment-specific source-package paths.

## Custom Packages

Existing custom-package JSON arrays remain supported. The new version 2 format uses an
object containing `version` and `packages`, and represents licenses with an object:

```json
// Swift Package List 4
[
    {
        "kind": "remoteSourceControl",
        "identity": "example-package",
        "name": "ExamplePackage",
        "location": "https://github.com/example/example-package",
        "license": "The license text"
    }
]

// Swift Package List 5 (custom-packages version 2)
{
    "version": 2,
    "packages": [
        {
            "identity": "example-package",
            "name": "ExamplePackage",
            "location": "https://github.com/example/example-package",
            "license": { "raw": "The license text" }
        }
    ]
}
```

Version 2 entries are emitted with `kind: "custom"`; `branch` and `revision` are `nil`.
Only `identity` and `name` are required. A license can contain exactly one of `raw`, `file`
or `directory`. File and directory paths are resolved relative to the custom packages
file. See the [Custom Packages documentation](../CommandLineTool/CustomPackages.md) for examples.

## JSON Schemas

JSON schemas are now available for all configuration files. It is recommended to add the
matching `$schema` field, as shown in the examples below, for validation and completion
in editors that support JSON schemas (Xcode does not unfortunately):

```json
// Plugin Configuration
{
    "$schema": "https://raw.githubusercontent.com/felixherrmann/swift-package-list/master/Schemas/plugin.v2.schema.json",
    "version": 2,
    "targets": {}
}

// Custom Packages
{
    "$schema": "https://raw.githubusercontent.com/felixherrmann/swift-package-list/master/Schemas/custom-packages.v2.schema.json",
    "version": 2,
    "packages": []
}
```

## Tuist `Dependencies.swift` Support Removed

The legacy Tuist `Dependencies.swift` project type is no longer supported. For an
XcodeProj-based integration, migrate to a `Package.swift` manifest and point the tool at
the matching build directory:

```shell
// Swift Package List 4
swift-package-list Tuist/Dependencies.swift

// Swift Package List 5
swift-package-list Tuist/Package.swift --custom-source-packages-path Tuist/.build
```

For Tuist projects using Xcode's default package integration, continue to use `Project.swift`.

## Makefile Removed

The Makefile got removed, so `make install`, `make update` and `make uninstall` are no
longer available. You can still build and install the command-line tool manually by
running the following commands from the repository's root directory:

```shell
swift build --configuration release --product swift-package-list
sudo mkdir -p /usr/local/bin
sudo install -m 755 .build/release/swift-package-list /usr/local/bin/swift-package-list
```

To update a manual installation, check out the newer version and repeat these commands.
